Lagrangian view

常见解法会引入 Lagrange multiplier。

粗略写成：

如果 cost 超过限制，lambda 变大，策略会更重视安全；如果 cost 很低，lambda 可以变小，策略有更多空间追求任务成功。

这个思路直觉上不错，但实现里有几个麻烦点：

  • cost estimate 本身有噪声
  • lambda 更新可能不稳定
  • 约束满足通常只是期望意义上的
  • 训练时安全不等于部署时安全
  • rare catastrophic failure 很难靠平均 cost 捕捉

最后一点很重要。一个策略如果 99 次很安全，1 次严重撞机，平均 cost 可能看起来还行，但真实系统不能接受。

所以 Lagrangian 方法更适合处理“可统计的软约束”，不适合单独承担所有安全责任。

hard constraints

有些约束不能只靠 loss。

比如：

  • joint limit
  • workspace boundary
  • maximum velocity
  • emergency stop
  • human safety zone

这些更适合放在 controller 或 safety filter 里，作为 hard constraint。

也就是说，策略可以输出一个动作，但 runtime system 需要判断这个动作能不能执行：

如果动作不合法，就要 clip、project、replace，或者直接 stop。

这会引入一个现实问题：训练算法以为自己输出了 raw_action，但真实机器人执行的是 executed_action。如果日志里不记录这两者的差异，后面很难分析策略到底学到了什么。

所以 constrained RL 和 runtime safety 最好不是两套互不相干的东西。算法侧要知道哪些动作经常被过滤，系统侧要把过滤原因写回数据。

constraint specification

constrained RL 的难点不只是算法，还有约束怎么写。

约束太松，没用。
约束太紧，策略学不到东西。
约束写错，系统会优化一个奇怪的代理目标。

一些比较容易写清楚的约束：

  • 速度上限
  • 力/力矩上限
  • workspace 边界
  • collision count
  • task timeout
  • intervention count

一些比较难写清楚的约束：

  • “动作看起来自然”
  • “不要让人觉得危险”
  • “不要弄乱桌面”
  • “失败后容易恢复”

后一类往往需要 human feedback、failure labeling 或者更细的环境状态定义。只靠一个标量 cost 很难表达。

这也是为什么具身智能里的 safety 不会只停留在 RL objective。它需要感知、日志、评估协议和人类介入一起配合。

evaluation

如果用了 constrained RL，评估时不能只报 success rate。

至少要同时报：

  • success rate
  • average cost
  • constraint violation rate
  • worst-case violation
  • intervention rate
  • hard reset count
  • unsafe stop count

其中 worst-case violation 很容易被忽略，但它很关键。很多安全问题不是平均意义上的，而是尾部风险。

所以 constrained RL 的评估也应该和 benchmark design 那篇连起来：任务定义、cost 定义、失败类型和日志协议都要写清楚。

relation to robotics

在机器人里，我觉得 constrained RL 更像一座桥。

一边是算法：

  • CMDP
  • Lagrangian optimization
  • safe policy optimization
  • offline-to-online fine-tuning

另一边是系统：

  • safety filter
  • controller limit
  • watchdog
  • fallback behavior
  • intervention logging

只做算法，可能部署不了。只做系统过滤，policy 又可能不知道自己为什么总被拦。

小结

constrained RL 可以先记：

  • 普通 RL 最大化 reward，constrained RL 同时看 cost budget
  • CMDP 把 reward return 和 cost return 分开
  • Lagrangian 方法能处理软约束，但不能保证所有硬安全
  • 机器人里的 hard constraints 应该放进 runtime system
  • safe exploration 要关心哪些状态不好恢复
  • cost specification 本身就是难题
  • 评估要同时报 success、violation、intervention、reset 和 worst-case failure

这篇补完后，RL 这条线从 reward、exploration、imitation、fine-tuning 接到了 safety constraints。后面再看具身智能时，runtime safety 就不只是工程补丁，而是和优化目标、数据闭环连在一起的东西。
